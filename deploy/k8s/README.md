# Выкат в Kubernetes

Требования к кластеру: **Cilium** (политики — `CiliumNetworkPolicy`),
**Gateway API** (внешний вход — `HTTPRoute`), класс хранения `local-path`.

```bash
kubectl apply -k deploy/k8s/gateway           # внешний вход, один раз на кластер
kubectl apply -k deploy/k8s/monitoring        # скрейп метрик, если есть prometheus-operator
kubectl apply -k deploy/k8s/base              # сам сервис
kubectl apply -k deploy/k8s/overlays/examples # плюс Telegram-бот
```

Секреты применяются отдельно, до первого `apply` — см. ниже.

## Внешний вход

`deploy/k8s/gateway` ставится **отдельно и обычно один раз**: у Gateway свой
жизненный цикл. Внешний адрес и сертификат переживают приложение —
пересоздавать `vulnscan` можно сколько угодно, адрес меняться не должен.

**Если Gateway в кластере уже есть — не применяйте этот каталог.** Пропишите
существующий в `base/80-httproute.yaml`. Второй Gateway означает второй
внешний адрес и второй сертификат на тот же домен.

Перед применением убедитесь, что у Cilium включён Gateway API:

```bash
kubectl get gatewayclass
```

Нужен класс `cilium` со статусом `ACCEPTED: True`. Пустой список означает, что
не установлены CRD Gateway API; класс без принятия — что у Cilium не включён
`gatewayAPI.enabled`.

Дальше нужен сертификат. Через cert-manager — аннотация на Gateway; вручную,
чтобы поднять прямо сейчас:

```bash
kubectl -n gateway create secret tls vulnscan-tls --cert=tls.crt --key=tls.key
```

И проверка, что адрес выдан:

```bash
kubectl -n gateway get gateway vulnscan -o wide
```

Пустой `ADDRESS` на bare-metal означает, что некому его выдать: нужен
`CiliumLoadBalancerIPPool` и анонс (L2 или BGP). Gateway при этом создан и
выглядит нормально — причина только в `status`.

## Это не перевод compose на другой язык

Так кажется, и это главная ловушка майлстоуна. В `docker-compose.yml` живут не
только команды запуска, но и **гарантии безопасности**: сеть без выхода
наружу, временные файлы в памяти, права процесса. Каждая переехала своим
механизмом, и почти каждая умеет молча не сработать.

Неверный `image:` роняет под — это видно. Не применившаяся политика не роняет
ничего: воркер работает, файлы проверяются, и только выход в интернет у него
остался.

Поэтому на манифесты есть тесты (`tests/test_k8s_manifests.py`, входят в
`make test`): лимиты, `securityContext`, тома в памяти, отсутствие токена
кластера, отсутствие выхода наружу у воркера, порты метрик. Каждый проверен
намеренной поломкой манифеста.

## Секреты

Базовый набор ожидает три объекта, и создаются они **из тех же файлов, что
читает compose** — `deploy/.env`, `deploy/config/keys.json`,
`deploy/secrets/delivery.json`:

```bash
sh deploy/k8s/secrets.sh              # база
sh deploy/k8s/secrets.sh --with-bot   # плюс оверлей examples
```

Скрипт идемпотентен: повторный запуск обновляет значения.

**Почему не манифест со значениями.** Копия секретов в YAML была бы вторым
источником правды. Второй источник расходится с первым молча, и узнаётся это
на ротации ключа — когда сервис остаётся на старом, а вы уверены, что
поменяли. Плюс файл с боевыми ключами в дереве репозитория живёт ровно до
первой невнимательности с `git add -f`.

В репозитории лежит только шаблон (`base/secrets.example.yaml`), и в сборку он
**не входит**: попав в неё, он перезаписал бы настоящие ключи заглушками при
первом же `apply -k`.

**Адрес базы скрипт переписывает.** В `.env` он `postgres:5432` — имя из
compose. Без замены на `postgres.vulnscan.svc` writer не подключится, а
выглядеть это будет как отставание истории: вердикты считаются, в базу не
едут.

**`defaultMode` не сужайте до `0400`.** Соблазн понятный — секрет же. Процессы
работают под uid 10001, владелец файла root, и чтения не будет. Проявляется
это не ошибкой доступа, а `degraded` в реестре ключей и `503` на каждой
загрузке, то есть далеко от причины.

### Про Secrets Store CSI Driver

Сейчас используются штатные `Secret`, то есть значения лежат в etcd. Переход
на CSI-драйвер — замена `volumes[].secret` на `volumes[].csi` плюс
`SecretProviderClass`; в коде не меняется ничего, пути монтирования те же.

Драйвер сам по себе ничего не хранит — ему нужен провайдер (Vault и подобные).
Заводить его имеет смысл вместе с решением, где будут жить секреты, а не
раньше.

### Ротация ключей

`KeyRegistry` перечитывает файл по mtime, без перезапуска. Но у notifier ключи
смонтированы через `subPath` — два разных Secret в один каталог иначе не
положить, — а **`subPath` не получает обновлений Secret**. Ротация там требует
`kubectl rollout restart deployment/notifier`.

У gateway монтируется каталог целиком, обновление доезжает само (до минуты).

## Что нужно заменить перед выкатом

| Где | Что |
|---|---|
| `base/80-httproute.yaml` | `parentRefs` — ваш Gateway и его listener, `hostnames` |
| `base/10-config.yaml` | `KNOWN_TENANTS`, адрес коллектора телеметрии |
| `base/*.yaml` | `image:` — namespace реестра и тег |
| `base/20-network-policies.yaml` | namespace мониторинга, если он не `observability` |

В `80-httproute.yaml` стоят заведомо неверные значения (`ЗАМЕНИТЕ-…`) — чтобы
выкат без правки не прошёл молча. Что именно туда подставить и как узнать
значения — расписано в самом файле.

Файлы базы пронумерованы в порядке выката. На результат номера не влияют:
kustomize раскладывает объекты по видам сам. Это порядок для человека.

### Маршрут применился, а трафика нет

Самая частая причина — Gateway не разрешил привязку из чужого namespace. У его
listener'а должно быть `allowedRoutes.namespaces.from: All` либо `Selector`,
выбирающий `vulnscan`. `kubectl apply` при этом проходит, объект создан, и
единственное место, где видно отказ, — статус маршрута:

```bash
kubectl -n vulnscan get httproute gateway -o yaml | grep -A5 conditions
```

Вторая причина — `hostnames` маршрута не пересекается с hostname listener'а
(`NoMatchingListenerHostname`).

## Проверить, что изоляция действительно есть

Тесты проверяют манифесты. Работу проверяет только запуск:

```bash
kubectl -n vulnscan exec deploy/worker -- \
    python -c "import socket; socket.create_connection(('1.1.1.1', 443), 3)"
```

Должно закончиться таймаутом. Отброшенные потоки видны в Hubble — он же
показывает, что политика **сработала**, а не что трафика не было:

```bash
hubble observe --namespace vulnscan --verdict DROPPED
```

## Доставка копий в чужой S3 (Yandex Object Storage)

Настройка живёт в двух местах, и разделение несущее: **адрес — это политика,
учётные данные — секрет**. Политику читают gateway и воркер, а воркер
разбирает враждебные файлы; ключ доступа к чужому хранилищу ему знать нельзя.

### 1. Учётка в Yandex Cloud

Сервисному аккаунту нужна роль **`storage.uploader`**, а не `storage.editor`:
запись без чтения и удаления. Тогда компрометация сервиса даёт мусор в вашем
префиксе, а не чтение и подмену чужих документов. Дальше — статический ключ
доступа (`Access key` + `Secret key`).

### 2. Ключи — в `deploy/secrets/delivery.json`

```json
{
  "yandex-drop": {
    "access_key": "YCAJE...",
    "secret_key": "YCM..."
  }
}
```

`yandex-drop` — это `credentials_id`, на него будет ссылаться политика.

### 3. Приёмник — в `deploy/config/policies.json`, у ТЕНАНТА

```json
{
  "telegram-bot": {
    "delivery": {
      "backend": "s3",
      "endpoint": "https://storage.yandexcloud.net",
      "bucket": "ваш-бакет",
      "prefix": "vulnscan/",
      "region": "ru-central1",
      "credentials_id": "yandex-drop",
      "key_template": "{filename}-Проверено-{verdict}-{sha}{ext}"
    }
  }
}
```

Три места, где легко ошибиться, и все три отказывают молча:

**Ключ верхнего уровня — имя тенанта, а не идентификатор ключа доступа.**
`telegram-bot`, а не `telegram-bot-1`. Промах означает `delivery: None` у
реального тенанта — воркер просто не ставит задание на выгрузку, без единой
строки в логе.

**`credentials_id` должен совпадать** с именем записи в `delivery.json`.

**`{filename}` требует `{ext}` в шаблоне.** Имя подставляется без расширения,
и без `{ext}` объекты уедут в бакет без него.

Проверить всё это до выката:

```bash
make config-check
```

### 4. Разложить по кластеру

```bash
sh deploy/k8s/config.sh
```

Не `kubectl create configmap` напрямую. Та команда кладёт в кластер что угодно:
JSON с пропущенной скобкой уедет молча и останется там жить. Сервис при этом
**не падает** — он пишет ERROR и работает на значениях по умолчанию, то есть
проверяет файлы по чужим порогам и не выгружает копии. В `kubectl get pods`
всё зелёное.

Скрипт разбирает файл настоящим загрузчиком сервиса (годный JSON и годная
политика — разные вещи: опечатка в имени поля даёт валидный JSON и
неработающий приёмник) и печатает, сколько тенантов и у скольких из них есть
приёмник. Ноль приёмников при настроенной политике виден сразу.

```bash
sh deploy/k8s/secrets.sh
```

Перезапуск notifier сделает Reloader — у всех рабочих объектов стоит
`reloader.stakater.com/auto: "true"`. **Если Reloader в кластере не
установлен**, перезапустите руками:

```bash
kubectl -n vulnscan rollout restart deployment/notifier
```

Почему именно notifier: `delivery.json` смонтирован через `subPath` (два
разных Secret в один каталог иначе не положить), а **такие монтирования
обновлений Secret не получают вовсе**. Без перезапуска notifier останется со
старыми учётными данными, и выглядеть это будет как неверный ключ.

Политика при этом подхватывается сама и без рестарта — см. ниже.

### 5. Убедиться, что поехало

```bash
kubectl -n vulnscan logs deployment/notifier | grep -i копи
```

Нужна строка «копия выгружена в хранилище клиента». Если её нет, а файлы
проверяются — смотрите в лог воркера при старте:

```
"политики тенантов загружены", tenants: 1, с_приёмником: 1
```

`с_приёмником: 0` при настроенном приёмнике означает ровно одно: блок
`delivery` лежит не у того тенанта.

### Когда включите политики

Notifier ходит наружу — в `policies/network-policies.yaml` у него уже есть
разрешение на 443 и DNS. Зато ему нужен работающий резолвер:
`storage.yandexcloud.net` должен резолвиться, иначе выгрузка встанет с
ошибкой имени, а не доступа.

## Корень только для чтения: где это стоило тома

`readOnlyRootFilesystem: true` стоит у всех контейнеров. В compose он был
только у воркера, поэтому остальные впервые работают так именно здесь — и два
сервиса на этом спотыкались:

**clamd** запускается через `/init-unprivileged`, а не штатный `/init`.
Последний делает `chown -R` на каталоге баз и падает под non-root, уводя за
собой весь под. Владельца тома и так выставляет `fsGroup`.

**cvdmirror** получил том на `/home/cvd`: `cvdupdate` держит конфигурацию и
журнал в домашнем каталоге. Том эфемерный намеренно — `entrypoint.sh`
пересоздаёт конфигурацию при каждом старте. В `/db` его класть нельзя: этот
каталог зеркало раздаёт наружу по HTTP.

Сокет clamd лежит в `/tmp` (`LocalSocket /tmp/clamd.sock`), поэтому том на
`/tmp` обязателен: без него clamd не поднимет сокет, а в логе будет только
«Can't connect to clamd».

gateway, notifier и writer с корнем только для чтения работают без томов —
проверено запуском образов.

## Если DNS не разрешён, ломается всё — но по-разному

Самая дорогая находка выката. `default-deny` закрывает и DNS, поэтому его
разрешают явно. Но правило по меткам пода CoreDNS совпадает не всегда: если
Cilium не подменяет kube-proxy, обращение к ClusterIP не транслируется в адрес
пода, и Cilium видит назначение как `world`.

В Hubble это выглядит так:

```
clamd-0 <> 10.43.0.10 (world) policy-verdict:none EGRESS DENIED
```

`(world)` рядом с адресом из диапазона Service — и есть признак. Поэтому в
`20-network-policies.yaml` DNS разрешён двумя путями: по меткам пода и по
диапазону Service. Второй нужно подставить свой:

```bash
kubectl -n kube-system get svc kube-dns -o jsonpath='{.spec.clusterIP}'
```

**Последствия расходятся веером, и ни одно не указывает на DNS.** Отвалившийся
DNS-прокси означает, что Cilium не видит ответы резолвера, а значит не знает,
какие адреса стоят за `toFQDNs`. Зеркало баз упирается в

```
cvdmirror-0 <> 151.101.0.223:443 (world) EGRESS DENIED (TCP Flags: SYN)
```

застревает на первом обновлении и не поднимает HTTP-сервер. А clamd, который
ходит к зеркалу, сообщает

```
Can't download daily.cvd ... Could not connect to server
```

— и это чистая правда: слушать порт некому. Три разных симптома, один корень,
и начинать разбор надо с самого нижнего.

## Метрики

```bash
kubectl apply -k deploy/k8s/monitoring
```

Отдельным компонентом, потому что `PodMonitor` — CRD prometheus-operator: в
кластере без него база не развернулась бы из-за мониторинга. `PodMonitor`, а
не `ServiceMonitor`: у воркера, notifier и writer Service нет и не нужно.

**Перед применением — две проверки, обе про тихий отказ.** Объект создаётся,
Prometheus его не видит, целей нет — и это неотличимо от «метрик нет».

Какую метку ваш Prometheus требует от мониторов (у kube-prometheus-stack по
умолчанию `release: <имя релиза>`):

```bash
kubectl get prometheus -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}: {.spec.podMonitorSelector}{"\n"}{end}'
```

Значение ставится в `labels` в `monitoring/kustomization.yaml`. `{}` в выводе
значит, что метка не нужна.

Из каких namespace он их берёт:

```bash
kubectl get prometheus -A -o jsonpath='{range .items[*]}{.spec.podMonitorNamespaceSelector}{"\n"}{end}'
```

**Имя job переписывается.** Панели и алерты ищут сервисы по
`job=~"vulnscantg.*"`, а PodMonitor по умолчанию называет job
`vulnscan/vulnscantg`. Цели при этом зелёные, метрики собираются, а панели
пусты. Поэтому в мониторах стоят `relabelings`, дающие те же имена, что в
compose; тест сверяет их с `deploy/lgtp/prometheus/prometheus.yml`.

**Политики пускают скрейп из `observability`.** Если Prometheus живёт в
другом namespace (у kube-prometheus-stack обычно `monitoring`), поменяйте имя
в `policies/network-policies.yaml` — во всех правилах сразу, тест следит,
чтобы оно было одно.

Проверить — в самом Prometheus:

```
up{job=~"vulnscantg.*"}
```

Семь целей: gateway, worker, deepscan, notifier, writer, cvdmirror, bot. Все
со значением 1.

## Версии образов

Тег задаётся в одном месте — `base/kustomization.yaml`, секция `images`:

```yaml
images:
  - name: dato1/vulnscantg-gateway
    newTag: v2.0.0
```

Поменяли, применили — поды перезапустятся сами, спецификация изменилась.

**`latest` не обновляется предсказуемо.** Kubernetes перекачивает его только
потому, что для плавающего тега умолчание `imagePullPolicy` — `Always`. Стоит
указать `IfNotPresent` явно (а это соблазнительно: «зачем ходить в реестр
каждый раз»), и узел навсегда останется с той версией, что у него уже есть.
`rollout restart` при этом отработает успешно, поды пересоздадутся, версия не
изменится — выглядит так, будто выкатили не то, что собрали.

Поэтому `imagePullPolicy` в манифестах не задан вовсе: умолчание здесь умнее
любого явного значения. На это есть тест.

Разово перевести на конкретную версию, не трогая манифесты:

```bash
kubectl -n vulnscan set image deployment/gateway gateway=dato1/vulnscantg-gateway:v2.0.0
```

Проверить, что выкачено на самом деле, — по логу при старте: сервис пишет два
поля, `version` (версия исходников) и `image_tag` (чем помечен образ). Они
расходятся законно, поэтому нужны оба.

## Перезапуск при смене конфигурации

У всех Deployment и StatefulSet стоит `reloader.stakater.com/auto: "true"` —
[Stakater Reloader](https://github.com/stakater/Reloader) перезапускает объект,
когда меняется ConfigMap или Secret, на который тот ссылается. Ставить его в
кластер необязательно: без него аннотация просто ничего не делает, а
перезапускать нужно руками.

Нужно это там, где обновление не приходит само:

* **переменные окружения** читаются один раз при старте;
* **секреты через `subPath`** (`keys.json` и `delivery.json` у notifier) не
  обновляются вообще — это ограничение Kubernetes, а не наша недоработка.

Без перезапуска ротация ключа выглядит завершённой: объект в кластере новый,
процесс работает со старым, и выясняется это на первом подписанном запросе.

**Исключение — `vulnscan-policies`.** На нём стоит
`reloader.stakater.com/ignore: "true"`, и это принципиально: политики и веса
перечитываются на живую по mtime файла, ради чего механизм и сделан — правка
порогов не должна ронять приём файлов. Автоперезапуск отменил бы его: вместо
горячей перезагрузки поды уходили бы в рестарт при каждой правке политики.

Снаружи разницу почти не видно — кроме коротких отказов на приёме. То есть
механизм остался бы, тесты на него остались бы, а работало бы совсем другое.

## Базы антивируса: срок и диагностика

clamd стартует на базах, которые лежат в его образе, и не ждёт зеркала. Но
у этих баз есть срок: через 7 суток от сборки они считаются непригодными,
`/readyz` отдаёт `503`, и проба готовности выводит из ротации **все** поды
gateway разом. Сервис перестаёт принимать файлы, хотя всё остальное работает.

Поэтому зеркало обязано качать. Если не качает, при неудачном обновлении
оно само пишет причину:

```bash
kubectl -n vulnscan logs cvdmirror-0 | grep "проверка доступа к CDN"
```

То же на живом поде, без перезапуска:

```bash
kubectl -n vulnscan exec cvdmirror-0 -- python3 /usr/local/bin/probe.py
```

`403` означает, что CDN ClamAV закрыт для этой сети: изнутри кластера баз не
получить никакими настройками, нужен выход через другую сеть. Таймаут — нет
выхода наружу вовсе.

Сколько осталось до отказа — по возрасту баз, который отдаёт сам сервис:

```bash
kubectl -n vulnscan exec deploy/gateway -- python -c "import urllib.request,json;print(json.load(urllib.request.urlopen('http://localhost:8080/readyz'))['av_db'])"
```

`age_h` больше 168 — непригодны.

## Открытые вопросы

**`/readyz` и базы антивируса (M11.11).** Проба готовности gateway смотрит на
`/readyz`, который отдаёт `503` при непригодных базах. Для одного процесса это
правильный fail-closed. В кластере это выводит из ротации **все** поды разом, и
сервис перестаёт отвечать вообще, вместо того чтобы отвечать отказом на
проверку. Оставлено осознанно — принять файл, который мы не можем проверить,
хуже, — но если вам нужно иначе, менять надо `/readyz` в коде, а не пробу.

**gVisor (M11.4).** `runsc` в манифестах не задан. Включается добавлением
`runtimeClassName` воркеру и deepscan — остальным не нужно: gateway под
песочницей ничего не выигрывает, а латентность теряет.


**`local-path` привязывает том к узлу.** Под, переехавший на другой узел, своих
данных не увидит. Для одной реплики это приемлемо; для Redis это означает, что
переживание переезда пода надо проверить до того, как в очереди окажутся
принятые задачи.
