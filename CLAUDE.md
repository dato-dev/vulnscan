# CLAUDE.md — правила работы с кодовой базой vulnscantg

Сервис принимает недоверенные файлы (PDF, изображения, сканы) от чат-ботов и внешних
интеграций, обезвреживает их (CDR) и выдаёт вердикт. **Весь входной поток считается
враждебным.** Это определяет большинство правил ниже.

## Архитектура в двух словах

`gateway` (FastAPI) принимает файл → стримом считает sha256 → кладёт в объектное
хранилище → проверяет кэш вердиктов → ставит задачу в Redis Stream → ждёт результат
до `wait_ms`. Успел — отдаёт `200`, не успел — `202` и результат уходит вебхуком.
`worker` гоняет конвейер стадий и CDR. Общий код — в `packages/vscommon`.

Подробности и схемы: [docs/architecture.md](docs/architecture.md).

## Язык и инструменты

- Python 3.12, обязательные аннотации типов во всех публичных функциях.
- Форматирование и линт — `ruff` (`make fmt`, `make lint`). Не спорь с форматтером.
- Типы — `mypy --strict` для `packages/vscommon` и `services/*/app`.
- Асинхронность: gateway и воркер — `asyncio`. Блокирующие вызовы (парсеры, subprocess,
  clamd) заворачивай в `asyncio.to_thread`, никогда не вызывай напрямую в корутине.
- Конфигурация — только через `pydantic-settings` и переменные окружения.
  Никаких констант окружения в коде, никаких `os.getenv` вразброс.

## Логирование

Логирование — **только через стандартный `logging`**. Это жёсткое правило.

- В каждом модуле: `logger = logging.getLogger(__name__)`. Не заводи глобальный
  логгер с чужим именем, не используй `logging.info(...)` на root-логгере.
- `print()` в коде сервисов запрещён. Исключение — скрипты в `samples/`.
- Настройка выполняется один раз на старте процесса: `vscommon.logging.setup_logging()`.
  Библиотечные модули (`packages/vscommon/*`) конфигурацию логирования не трогают.
- Формат в проде — JSON (`LOG_FORMAT=json`), в разработке — human-readable (`console`).
- Идентификаторы протаскиваются через `contextvars`, а не через аргументы:
  `with log_context(scan_id=..., sha256=...):` — поля попадут во все записи внутри блока.
- Уровни: `DEBUG` — тайминги стадий и детали разбора; `INFO` — жизненный цикл скана
  (принят, завершён, коллбэк отправлен); `WARNING` — деградация (стадия упала, дедлайн
  истёк, движок недоступен); `ERROR` — сбой обработки задачи. Вердикт `malicious`
  логируется на `INFO` — это штатный исход, а не ошибка.
- Исключения логируются через `logger.exception(...)` внутри `except`, без ручного
  форматирования traceback.

### Что запрещено писать в логи

Сервис обрабатывает сканы паспортов и договоров. В логи **никогда** не попадают:

- содержимое файла или его фрагменты, включая извлечённый текст и base64;
- имя файла целиком (только расширение и длина) — оно часто содержит ПДн;
- полный sha256 в качестве идентификатора в общих логах — используй `sha256[:12]`;
- URL коллбэка с query-параметрами, заголовки авторизации, HMAC-подписи, ключи API;
- значения из EXIF/XMP-метаданных.

Если нужно отладить конкретный файл — используй `scan_id` и смотри артефакты в
хранилище, а не расширяй логи.

## Безопасность (самое важное)

- **Файл никогда не исполняется.** Только парсинг и перекодирование.
- Любой разбор недоверенного контента идёт в воркере, у которого **нет сетевого
  egress**, кроме Redis, S3 и коллбэка. Новые исходящие вызовы из стадий — не добавлять.
- У каждой стадии есть таймаут и лимит памяти. Стадия без таймаута не проходит ревью.
- Внешние утилиты запускаются только через `run_sandboxed()` из
  `services/worker/worker_app/sandbox.py` — там rlimits, timeout и `close_fds`. Прямой
  `subprocess.run` в стадиях запрещён.
- Временные файлы — только в `tmpfs` (`WORK_DIR`), с гарантированным удалением через
  `contextlib` и `finally`. Ничего не оседает на диске после обработки.
- Защита от бомб: лимиты на размер входа, на размер выхода CDR, на пиксельную площадь
  изображения, на глубину вложенности объектов PDF. Лимиты живут в `vscommon.limits`.
- Failure mode задаётся политикой тенанта, а не кодом стадии и не запросом клиента.
  Стадия сообщает «не смогла»; решение принимает `scoring.verdict_on_failure()` по
  `TenantPolicy`. **Никогда не добавляй в `ScanRequest` поля, которыми клиент может
  ослабить проверку** — режим отказа, пороги, отключение стадий. Всё это серверная
  конфигурация (`vscommon/policy.py`).
- Ни один путь исполнения, кроме успешно завершённой проверки, не имеет права дать
  вердикт `clean`. Новый `except`, возвращающий результат, — повод для теста на это.

## Правила для стадий конвейера

- Одна стадия — один файл в `services/worker/worker_app/stages/`, один класс,
  наследник `Stage`. Разбор конкретного формата, если он перерос файл, выносится
  в модуль рядом (`pdf_structure.py`) — стадия остаётся диспетчером.
- Любой обход недоверенной структуры — итеративный и с явным лимитом шагов.
  Рекурсия по специально вложенному документу даёт `RecursionError`, то есть
  падение стадии вместо признака.
- Разбор недоверенного объекта делай через `_get`/`_call`: битое поле в PDF это
  норма, а не исключительная ситуация, и логировать каждый отказ нельзя —
  один файл зальёт логи целиком.
- Стадия **не принимает решение** — она возвращает `list[Finding]`. Вердикт считается
  централизованно в `scoring.py`. Не добавляй в стадии `if ...: return "malicious"`.
- Коррелированные признаки объединяй в семейство (`CODE_FAMILIES` в
  `vscommon/weights.py`): внутри семейства в балл идёт только сильнейший.
  Складывать можно лишь независимые наблюдения, иначе одна поломка,
  замеченная тремя проверками, даёт тройной вес.
- Стадия **не назначает вес**. `ctx.add(stage, code, detail)` берёт балл и severity
  из таблицы (`vscommon/weights.py`). Новый код признака добавляй туда же — иначе
  он получит запасной вес и попадёт в `unknown_codes`. Для динамических кодов
  (YARA) используй `weight_key`.
- Стадия не должна падать наружу: любое исключение внутри превращается в
  `Finding(code="STAGE_FAILED", ...)` и `WARNING` в лог. Один сломанный парсер не
  роняет скан.
- Стадия, отдающая файл в C-код (pikepdf, Pillow, yara-python), обязана быть в
  `RISKY_STAGES` в `worker/worker_app/failure.py`. Оттуда возможен segfault, который
  исключением не ловится, и журнал попыток должен о нём знать.
- Новую внешнюю зависимость с сетевым доступом добавляй в `_INFRA_MODULES`
  (`vscommon/errors.py`), иначе её транзиторный сбой будет принят за порчу файла
  и задача закроется без повтора.
- Порядок стадий — от дешёвых к дорогим. Новую дорогую проверку ставь после `clamav`
  или переводи в асинхронный deep-scan.
- Стадию, без которой файл нельзя считать проверенным, добавляй в `ESSENTIAL_STAGES`
  (`worker/worker_app/scoring.py`). Не полагайся на вес `STAGE_FAILED`: он ниже порога и
  тонет. Именно поэтому недоступный clamd когда-то выдавал `clean` на всё подряд.
- У каждого `Finding` есть стабильный `code` в `SCREAMING_SNAKE_CASE`. Коды — часть
  публичного контракта, переименование = ломающее изменение API.

## Правила для CDR

- Профиль `strict` обязан быть безопасным by construction (растеризация), а не
  «удалили всё, что знаем». Не добавляй в него эвристики.
- Санитайзер всегда собирает **новый** файл, а не патчит исходный на месте.
- После санитизации результат прогоняется через `verify_sanitized()` — если в выходе
  снова находятся активные элементы, это `ERROR` и `sanitize_failed`, а не тихий успех.
- Неподдерживаемый формат — это вердикт `unsupported`, а не `clean`. Никогда не отдавай
  необработанный файл под видом обезвреженного.
- Непроверяемое (`UNSCANNABLE_VERDICTS`) в CDR не отправляется: пересобирать нечего,
  а падение санитайзера уводит задачу в ветку отказа и перезаписывает вердикт.
- Любой новый код, меняющий `result.verdict` после скоринга, обязан идти через
  `scoring.apply_failure()`. Прямое присваивание способно смягчить вердикт —
  именно так `encrypted` однажды превращался в `clean` при `fail-open`.

## API

- Ломающие изменения — только через новый префикс версии (`/v2/`).
- `verdict` и `score` разделены: сервис детектит, политику применяет клиент.
- Идемпотентность по `Idempotency-Key` = sha256 файла. Повтор не создаёт новый скан.
- Все ответы содержат `scan_id`; клиент логирует его у себя для трассировки.

## Документация и схемы

- Архитектурные решения документируются в `docs/`, схемы — **только Mermaid**
  в fenced-блоках ```mermaid. Картинки-скриншоты в репозиторий не кладём.
- Меняешь поток данных или добавляешь стадию — обнови соответствующую схему в
  `docs/architecture.md` в том же изменении.
- Типы схем: `flowchart` для компонентов и конвейера, `sequenceDiagram` для
  межсервисного взаимодействия, `stateDiagram-v2` для жизненного цикла скана.

## Тесты

- `pytest`, без сети. Redis и S3 в тестах — фейки из `tests/fakes.py`.
- Каждая новая стадия сопровождается тестом на срабатывание и тестом на «стадия упала».
- Каждый новый CDR-профиль сопровождается тестом: активный элемент есть на входе,
  его нет на выходе.
- Тестовые сэмплы генерируются скриптом `samples/make_samples.py`. **Реальные
  вредоносные файлы в репозиторий не коммитятся** — только синтетика и EICAR.

## Что делать не нужно

- Не добавляй новые зависимости-парсеры без обсуждения: каждый парсер — это новая
  поверхность атаки с собственной историей CVE. Если парсер всё-таки нужен,
  сервис обязан работать и без него: недоступная библиотека переводит проверку
  в деградированный режим с записью в `/readyz`, а не отключает её молча.
- Лимиты, защищающие сервис (частота, параллелизм, размер), — серверная политика
  тенанта. Частоту проверяй до чтения тела, иначе нагрузка уже принята.
- Всё, что вызывается из стадии, живёт в пуле потоков. Объект с внутренним
  состоянием (cookie libmagic, сокет clamd, скомпилированные правила) либо
  создаётся на поток, либо защищается блокировкой. Выбор по цене: блокировка —
  если стадия дешёвая, а объект дорого создавать; экземпляр на поток — если
  стадия дорогая, а объект дёшев. На каждый такой объект нужен тест на
  параллельные вызовы.
- Не выноси стадии в отдельные микросервисы «для масштабирования» — сетевой хоп на
  файл дороже самой проверки.
- Кэшируй признаки, а не вердикт: пороги и веса у тенантов разные, и общая запись
  с чужим вердиктом отдаёт неверный ответ. Вердикт пересчитывается на чтении через
  `vscommon.scoring`.
- Всё, что влияет на балл признака, обязано входить в ключ структурного кэша:
  версия правил, отпечаток таблицы весов, переопределения тенанта.
- Правила и веса перезагружаются на живом воркере. Любая новая конфигурация,
  влияющая на вердикт, обязана: компилироваться вне блокировки, при ошибке
  оставлять прежнюю версию и менять отпечаток в ключе кэша.
- Не логируй в горячем пути на уровне `INFO` больше одной записи на скан.
