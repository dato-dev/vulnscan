# Протокол vulnscantg

Документ описывает протокол так, чтобы по нему можно было написать клиента, **не
читая наш код**. Всё, что здесь сказано, — обязательства сервиса; всё, что
названо обязательным для клиента, обязательно и без него интеграция небезопасна.

Опорная реализация — [`packages/vulnscan_client`](../packages/vulnscan_client).
Она следует этому документу, а не наоборот: расхождение между ними — ошибка в
документе или в библиотеке, но не «особенность Python-клиента».

Руководство по подключению с примерами — [integration.md](integration.md).
Полное описание ручек и полей ответа — [api.md](api.md).

## Что должен уметь клиент

Минимум, ниже которого интеграция не работает:

1. подписать запрос и приложить три заголовка;
2. отправить файл и разобрать ответ — синхронный либо отложенный;
3. **отличить «безопасно» от «не заблокировано»**;
4. проверить подпись коллбэка, если результаты принимаются коллбэком;
5. **запросить вердикт своим ключом**, если файл грузился из браузера — см.
   [Загрузка из браузера](#загрузка-из-браузера). Всё, что пришло от страницы,
   включая `scan_id` и «чисто», написал браузер посетителя.

Третий пункт — единственная ошибка, которая не проявляется никак: интеграция
работает, тесты проходят, а непроверенные файлы принимаются как чистые.

## Аутентификация

Каждый запрос несёт три заголовка:

| Заголовок | Содержимое |
|---|---|
| `X-Vulnscan-Key` | идентификатор ключа, выданный вместе с секретом |
| `X-Vulnscan-Timestamp` | Unix-время в секундах, десятичное, без дробной части |
| `X-Vulnscan-Signature` | `sha256=<hex>` — HMAC-SHA256 в нижнем регистре |

Тенант в запросе **не передаётся**. Он выводится из ключа на стороне сервиса —
иначе клиент мог бы назваться чужим именем и получить чужие настройки.

### Что именно подписывается

Подписывается не запрос целиком, а строка, которую обе стороны собирают
одинаково. Схем две, и выбор между ними зависит от того, есть ли у сервиса
возможность прочитать тело до аутентификации.

**Канонический запрос** — для загрузки файла и для всех `GET`:

```
METHOD\nPATH\nKEY_ID
```

Метод в верхнем регистре, путь — с ведущей косой чертой и без строки запроса,
разделитель — символ перевода строки (`\n`, не `\r\n`). Кодировка UTF-8.

Пример байтов, которые подписываются для загрузки:

```
POST\n/v1/scan\nacme-prod
```

**Тело запроса** — для ручек, принимающих JSON. Подписывается ровно тот массив
байтов, который уходит в сеть: пересериализация после подписи ломает её,
поэтому подписывать надо уже готовое тело.

> Почему две схемы. Загрузка идёт `multipart/form-data`, и прочитать тело можно
> только целиком — то есть приняв неаутентифицированный файл в память. Сервис
> проверяет подпись до чтения тела, а значит подписать может только то, что
> видно из заголовков и строки запроса.

### Вычисление подписи

```
timestamp = текущее время в секундах
payload   = канонический запрос ИЛИ тело
mac       = HMAC-SHA256(secret, utf8(timestamp + "." + payload))
signature = "sha256=" + hex(mac)
```

Точка между отметкой времени и полезной нагрузкой обязательна. Без неё подпись
без отметки времени совпала бы с подписью, где отметка пуста, — и повтор старого
запроса стал бы возможен.

Секрет используется как последовательность байтов в UTF-8, без нормализации и
без декодирования из hex или base64.

### Окно времени

Расхождение часов допускается в пределах **300 секунд** в любую сторону. Больше —
`401`, и это не ошибка подписи, а защита от повторной отправки перехваченного
запроса.

Практическое следствие: клиент обязан иметь синхронизированное время. Первая
жалоба «подпись не сходится» в трёх случаях из четырёх — часы.

### Сравнение подписи

Сравнивать **только за постоянное время** (`hmac.compare_digest` и аналоги).
Обычное сравнение строк раскрывает подпись побайтово по времени ответа.

Подпись, содержащая символы вне ASCII, отклоняется до сравнения — иначе
сравнение падает исключением на неверных данных, а исключение внутри проверки
подписи легко превратить в отказ обслуживания.

## Вызовы

Все пути под `/v1`. Ломающие изменения приходят новым префиксом версии, поэтому
клиент может рассчитывать, что смысл ответа под `/v1` не поменяется.

### POST /v1/scan — отправить файл

`multipart/form-data` с двумя полями: `file` — сам файл, `meta` — JSON с
параметрами. Подпись — по каноническому запросу.

Заголовок `Idempotency-Key` — это **sha256 содержимого файла** в hex. Повтор с
тем же ключом не создаёт новую проверку, а присоединяется к существующей.
Ключ не выдумывается клиентом: он вычисляется из файла, поэтому два клиента,
приславшие один файл, получают один результат.

Поля `meta`, которые клиент вправе задавать:

| Поле | Значения | По умолчанию |
|---|---|---|
| `filename` | строка | обязательно; идёт только в определение типа, в ответ не возвращается |
| `mode` | `detect`, `sanitize`, `both` | `both` |
| `profile` | `light`, `standard`, `strict` | из политики тенанта |
| `wait_ms` | 0–10000 | 400 |
| `callback_url` | URL | нет |

**Чего в `meta` нет и не будет:** режима отказа, порогов балла, отключения
проверок. Это серверная политика тенанта. Клиент, который может ослабить себе
проверку, рано или поздно её ослабит — и не заметит.

Поле `tenant` в схеме существует, но присланное значение игнорируется: тенант
берётся из ключа.

### GET /v1/scan/{scan_id} — забрать результат

Подпись — по каноническому запросу с полным путём, включая идентификатор.

`404` означает одно из двух: скана нет или он принадлежит другому тенанту.
Различать эти случаи в ответе мы не будем — иначе перебор идентификаторов
показывал бы, какие сканы существуют у соседей.

### GET /v1/scan/{scan_id}/clean — скачать обезвреженную копию

Отдаёт байты, а не JSON. `409` — копии нет: либо запрашивали `mode=detect`,
либо файл непроверяем и пересобирать было нечего.

### POST /v1/scan/ref — проверить то, что уже лежит в хранилище

Для случая, когда файл уже в общем объектном хранилище и передавать его
повторно незачем. Подпись — **по телу**, потому что тело здесь JSON.

## Коды ответов

| Код | Что означает | Повторять? |
|---|---|---|
| `200` | вердикт готов | — |
| `202` | принято, результат позже: коллбэком или через `GET` | — |
| `400` | запрос не разобран | нет, повтор даст то же |
| `401` | подпись, ключ или окно времени | нет; проверьте часы |
| `404` | скан не найден либо чужой | нет |
| `409` | обезвреженной копии не существует | нет |
| `413` | файл больше разрешённого политикой | нет |
| `429` | превышена частота или число одновременных проверок | да, с задержкой |
| `5xx` | сбой на нашей стороне | да, с экспоненциальной задержкой |

Повторять имеет смысл только `429` и `5xx`. Повтор `4xx` не приближает успех, а
квоту расходует.

**`202` — не ошибка.** Это штатный исход: сервис не уложился в `wait_ms`.
Клиент, считающий `202` отказом, будет терять результаты на больших файлах.

## Модель ответа

Один и тот же объект возвращается из `POST /v1/scan`, из `GET /v1/scan/{id}` и
приходит телом коллбэка. Полное описание полей — в [api.md](api.md); здесь то,
без чего клиента не написать.

### Статус и вердикт — разные вещи

`status` отвечает на вопрос «проверка закончилась?», `verdict` — «что нашли».

| `status` | Смысл |
|---|---|
| `queued` | принято, ещё не начали |
| `scanning` | в работе |
| `done` | закончено, `verdict` осмыслен |
| `failed` | проверка не состоялась |
| `manual_review` | не удалось после повторов, ждёт человека |

При `queued` и `scanning` вердикта ещё нет — читать его нельзя.

### Вердикты

| `verdict` | Что это значит для клиента |
|---|---|
| `clean` | проверен, признаков нет |
| `suspicious` | признаки есть, порог блокировки не пройден |
| `malicious` | блокировать |
| `unsupported` | формат не поддержан — **не проверен** |
| `encrypted` | зашифрован, разобрать нельзя — **не проверен** |
| `error` | проверка сорвалась — **не проверен** |

### Главное правило разбора

> **`verdict != "malicious"` не означает «безопасно».**

Три вердикта — `unsupported`, `encrypted`, `error` — говорят, что файл **не был
проверен**. Он не заблокирован, но и безопасным не является.

Список безопасного задаётся **положительно**, а не через список запрещённого:

```
safe = verdict in {"clean"}
```

Причина простая: вердикты добавляются. Незнакомый вердикт, полученный старым
клиентом, при положительном списке окажется небезопасным — то есть ошибка
приведёт к лишней строгости, а не к пропуску. Список запрещённого дал бы
обратное, и узнали бы вы об этом по последствиям.

Это же правило — причина, по которой в опорной библиотеке `blocked` и `safe`
существуют раздельно, а не как отрицание друг друга.

## Коллбэки

Если в `meta` задан `callback_url`, готовый результат приходит `POST`-запросом на
этот адрес. Тело — тот же объект, что вернул бы `GET /v1/scan/{id}`.

Адрес проверяется **на приёме файла**, а не при доставке: иначе файл был бы
принят и проверен, а результат девать некуда. Разрешённые хосты задаются при
выдаче ключа; адреса метаданных облаков заблокированы всегда.

### Заголовки коллбэка

| Заголовок | Содержимое |
|---|---|
| `X-Vulnscan-Timestamp` | Unix-время подписи |
| `X-Vulnscan-Signature` | `sha256=<hex>` по **телу** запроса |
| `Content-Type` | `application/json` |

Идентификатора ключа в коллбэке нет: получатель знает, каким ключом он у нас
зарегистрирован. Схема подписи та же — `HMAC(secret, timestamp + "." + body)`.

### Проверка обязательна

> Эндпоинт без проверки подписи принимает вердикт **от кого угодно**. «Файл
> чист» пришлёт тот, кто этот файл и подсунул.

Порядок проверки:

1. взять **сырые байты** тела — до разбора JSON. Разбор и повторная сериализация
   меняют байты (порядок ключей, пробелы, экранирование), и подпись не сойдётся;
2. проверить расхождение времени — не больше 300 секунд;
3. сравнить подпись за постоянное время;
4. только после этого разбирать JSON.

Пункт 1 — самая частая ошибка на этой стороне: во многих фреймворках тело уже
разобрано к моменту, когда до него доходят руки, и его приходится запрашивать
отдельно.

### Повторы

Отвечайте `2xx` как только приняли результат. Любой другой код мы разбираем так:

| Ответ получателя | Что делаем |
|---|---|
| `2xx` | доставлено |
| `408`, `425`, `429`, `500`, `502`, `503`, `504` | повторим |
| прочие `4xx` | отказ по существу, повторять не будем |
| нет соединения, таймаут | повторим |

Повторов до **десяти**, задержка удваивается от 2 секунд и упирается в 10 минут —
в сумме около получаса. Дальше результат уходит в дедлеттер с признаком
`CALLBACK_FAILED` и ждёт разбора человеком.

Таймаут на запрос — 10 секунд. Долгая обработка на вашей стороне превращается в
повторную доставку: примите и подтвердите, обрабатывайте потом.

### Доставка возможна повторно

Один и тот же результат может прийти дважды: мы повторяем, когда не уверены, что
доставили. Обработчик обязан быть идемпотентным по `scan_id`.

## Загрузка из браузера

Схема для случая, когда файл идёт от посетителя прямо к нам, минуя сервер
сайта. Ключей здесь два, и путать их нельзя.

| Ключ | Где лежит | Что умеет |
|---|---|---|
| публичный (`public`) | открыто в HTML страницы | получить талон, и только |
| секретный | на бэкенде сайта | всё остальное, включая проверку результата |

### Порядок

1. Браузер просит талон: `POST /v1/tickets` с заголовком `X-Vulnscan-Key`
   (публичный ключ). Подписи нет — вместо неё проверяется `Origin`.
2. Браузер грузит файл: `POST /v1/scan` с заголовком `X-Vulnscan-Ticket`.
   Талон одноразовый, живёт минуты и знает свой предел размера.
3. В ответ приходит `scan_id`, форма отправляется с ним.
4. **Бэкенд сайта запрашивает результат сам** — `GET /v1/scan/{scan_id}` со
   своей подписью.

### Четвёртый шаг обязателен

> Браузер посетителя целиком под его контролем. Он отправит форму с любым
> `scan_id` и любым «чисто». Вердикт становится доказательством только тогда,
> когда его запросил ваш сервер своим ключом.

Виджет без этого шага — украшение. Так же устроена любая капча: проверка на
стороне сервера не «продвинутое использование», а половина механизма.

Три следствия, которые стоит знать заранее.

**Файл забирайте по тому же `scan_id`**, по которому проверяли вердикт
(`GET /v1/scan/{scan_id}/clean`). Тогда подмена идентификатора безвредна: вы
получите ровно тот файл, который проверили. Брать имя, размер или что-либо
ещё из формы — значит доверять браузеру там, где только что решили не
доверять.

**`scan_id` не идентифицирует отправку формы.** Проверка идемпотентна по
sha256: двое посетителей, приложивших один и тот же документ, получат один
идентификатор. Связывать его со своей записью нужно у себя.

**Публичным ключом результат не прочитать.** Подписать им нельзя — его секрет
знает каждый, кто открыл исходный код страницы, — и сервис отвергает такой
ключ до сравнения подписи. Иначе посетитель читал бы вердикты по чужим
идентификаторам.

### Виджет: что считается ломающим изменением

Скрипт раздаём мы, а у сайта нет способа откатиться: он подключил
`<script src=...>` и получает то, что мы отдали сегодня. Поэтому версия стоит
**в пути** — `/widget/v1/loader.js` — и работает правило:

- **совместимое** едет на том же адресе: новый тип сообщения, новое
  необязательное поле, изменение внешнего вида фрейма;
- **ломающее** получает новый путь: переименование или удаление типа
  сообщения, смена имени скрытого поля, смена параметров фрейма.

Типы сообщений, которые фрейм шлёт странице:

| Тип | Когда | Поле формы |
|---|---|---|
| `ready` | фрейм загрузился | очищается |
| `busy` | файл выбран, идёт проверка | очищается |
| `checked` | проверка завершена | заполняется |
| `pending` | не успели за отведённое время | заполняется |
| `blocked` | вердикт `malicious` | очищается |
| `unchecked` | проверка не состоялась | очищается |

Пустое поле означает «вложения нет» — безопасное состояние. Непроверенный файл
не должен выглядеть как проверенный, поэтому `unchecked` очищает поле так же,
как `blocked`.

Ответы несут заголовок `X-Vulnscan-Widget` с версией: при разборе «у нас всё
сломалось» иначе неизвестно, что лежит у сайта в кэше.

### CSP на стороне сайта

У сайта с жёсткой политикой безопасности виджет не заработает, пока в неё не
добавлены две директивы. Обе обязательны, остального нам не нужно:

```
script-src  https://scanner.example;
frame-src   https://scanner.example;
```

`script-src` — для загрузчика, `frame-src` — для самого фрейма. Адрес
подставьте свой: тот, с которого раздаётся `/widget/v1/loader.js`.

**Чего нам не нужно и просить не станем:**

| Директива | Почему не нужна |
|---|---|
| `connect-src` | запросы к нам идут из фрейма, то есть с нашего origin, а не со страницы |
| `img-src`, `font-src`, `style-src` | всё содержимое фрейма — внутри фрейма |
| `'unsafe-inline'`, `'unsafe-eval'` | загрузчик не использует ни то, ни другое |
| `form-action` | форму отправляет сайт, мы к ней не прикасаемся |

Просьба ослабить политику ради интеграции — повод насторожиться, и к нашей она
не относится. Если понадобилось что-то ещё — это ошибка в нашей документации,
и мы хотим о ней знать.

**Со стороны фрейма** политика своя, и её ставим мы: `default-src 'none'`,
запросы только к себе, встраивание только с origin вашего ключа
(`frame-ancestors`). Отдельно настраивать это не нужно — заголовок приходит с
документом.

### Отложенный результат в виджете

Крупный файл не укладывается в отведённое время, и загрузка отвечает `202`.
Прочитать вердикт фрейм не может — для этого нужна подпись, а публичным ключом
подписать нельзя.

Поэтому вместе с `202` приходит заголовок `X-Vulnscan-Status-Ticket`: талон на
наблюдение **за этим сканом**. По нему фрейм опрашивает
`GET /widget/v1/status?ticket=…`, пока проверка не закончится, и показывает
исход посетителю.

Талон наблюдения отличается от талона на загрузку двумя вещами, и обе
намеренные: он многоразовый (опрос — это несколько запросов) и живёт дольше
(ждёт конца проверки, а не выбора файла). Общее у них главное — он привязан к
одному предмету и ничего сверх него не открывает: ни вердикта чужого файла, ни
самого файла.

Ручка отдаёт три состояния — `checked`, `blocked`, `unchecked` — и ничего
больше. Ни балла, ни признаков: браузеру они не нужны, а решение всё равно
принимает бэкенд сайта своим ключом.

### Откуда приходит запрос на талон

Два случая, и в них разный `Origin`.

**Из фрейма виджета.** Фрейм живёт на нашем origin, поэтому его обращение к
`/v1/tickets` — same-origin, и браузер ставит **наш** адрес, а не адрес сайта.
Такой запрос принимается: загрузиться этот документ мог только на странице из
списка ключа, и следит за этим `frame-ancestors`, то есть браузер, а не мы.

**Прямым вызовом со страницы сайта**, без нашего фрейма. Тогда `Origin` — адрес
сайта, и он должен быть в списке ключа.

Путать эти случаи легко, и стоит это дорого: проверка, написанная только под
второй, отвечает «ключ сайта недействителен» на совершенно исправный ключ.

### Что защищает `Origin`, а что нет

Привязка публичного ключа к списку origin не даёт вставить его на чужой сайт.
Она **не** защищает от запросов мимо браузера: там заголовок подделывается
свободно. От этого защищают квоты — частота по ключу и суточный потолок, — и
путать эти две защиты не стоит.

## Совместимость

Что мы обязуемся не ломать в пределах `/v1`:

- **схему подписи** — порядок полей канонического запроса, разделители, точку
  между отметкой времени и нагрузкой;
- **имена заголовков**;
- **смысл существующих вердиктов и статусов**, а также коды признаков (`code` в
  `findings`): они часть контракта, переименование = новая версия;
- **смысл кодов ответа** из таблицы выше.

Что может измениться без смены версии:

- **добавление** вердиктов, статусов и кодов признаков. Поэтому список
  безопасного задаётся положительно, а незнакомое значение клиент обязан
  считать небезопасным;
- добавление полей в ответ. Неизвестные поля игнорируйте, а не падайте на них;
- значения по умолчанию, вычисляемые из политики тенанта.

Проверить свою реализацию на совпадение с нашей можно фиксированными векторами:
[../tests/vectors/protocol.json](../tests/vectors/protocol.json). Там секрет,
нагрузка, отметка времени и ожидаемая подпись — байт в байт, включая
канонический запрос. Реализация на любом языке обязана давать те же значения.
