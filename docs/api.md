# API

Все эндпоинты под `/v1`. Ответ и тело коллбэка — одна и та же модель `ScanResult`.

## POST /v1/scan — приём файла

`multipart/form-data`: поле `file` — сам файл, поле `meta` — JSON с параметрами.

```json
{
  "mode": "both",
  "profile": "standard",
  "wait_ms": 400,
  "callback_url": "https://bot.example/webhooks/vulnscan",
  "tenant": "team-a"
}
```

| Поле | Значения | Смысл |
|---|---|---|
| `mode` | `detect` / `sanitize` / `both` | нужен ли CDR |
| `profile` | `light` / `standard` / `strict` | глубина обезвреживания; опущено — берётся из политики тенанта |
| `wait_ms` | 0-10000 | сколько ждать синхронный ответ; ограничивается сверху политикой |
| `callback_url` | URL | куда прислать результат вебхуком |
Тенанта в запросе нет: он выводится **из ключа**, которым запрос подписан.
Присланное клиентом значение игнорируется — иначе выбором тенанта выбирались бы
и его пороги, и режим отказа.

По идентификатору ключа частота проверяется **до** чтения тела. Незнакомый ключ
попадает в общее строгое ведро.

### Чего в запросе нет и не будет

Режим отказа при сбое проверки (`fail-closed` / `suspicious` / `fail-open`) и пороги
скоринга — **серверная политика тенанта**, а не параметры запроса. Клиент не может
полем в теле отключить себе fail-closed. Присланные поля вида `on_timeout` молча
игнорируются. Настройка политики — через `POLICY_FILE`, пример:
[policies.example.json](../policies.example.json).

**Коды ответа:**

- `200` — результат готов, `status: done`, при `mode != detect` заполнен `sanitized`.
- `202` — не уложились в `wait_ms`, `status: queued`. Результат придёт на `callback_url`,
  либо забирается через `GET /v1/scan/{scan_id}`.
- `413` — файл больше лимита. Предел берётся из политики тенанта, но не выше
  общего; чтение обрывается на первом же превышающем чанке.
- `429` — превышена частота запросов либо число одновременных проверок. Заголовок
  `Retry-After` указывает, через сколько секунд повторять. Ограничения
  per-tenant: соседи по сервису на них не влияют.

## POST /v1/scan/ref — приём по ссылке

Тело — JSON `ScanRequest` с полем `source`. Требует HMAC-подписи. Используйте, когда
файл уже лежит в общем с сервисом бакете: тело не гоняется по сети дважды.

## GET /v1/scan/{scan_id}

Снимок состояния скана. Живёт 5 минут после завершения — и 7 суток, если задача
ушла в dead-letter: `404` на такой скан клиент не отличил бы от «всё хорошо».

### Статусы

| `status` | Смысл |
|---|---|
| `queued` / `scanning` | в работе |
| `done` | проверка завершена, `verdict` осмыслен |
| `failed` | проверка сорвалась, вердикт по политике отказа |

## GET /v1/scan/{scan_id}/clean

Отдаёт пересобранную копию. Хранилище наружу не светится: файл достаётся только
через сервис.

Копия существует для любого исхода, кроме заблокированного и непроверяемого —
там пересобирать нечего, и ответ будет `409` с указанием вердикта. Отдавать её
стоит даже для чистых файлов: она собрана заново, без активных элементов, и это
работает против того, чего мы ещё не умеем детектить.

Скан принадлежит тенанту ключа. Чужому отвечаем `404`, а не `403`: `403`
подтвердил бы существование скана и превратил бы ручку в способ проверять чужие
идентификаторы.

## Выкатка правил

`POST /v1/ops/rules/disabled` выключает одно правило по имени, не трогая файлы
и не выкатывая релиз; `DELETE /v1/ops/rules/disabled/{rule}?author=...`
возвращает его в работу. Автор и причина обязательны.

`GET /v1/ops/rules/canary` — что набор-кандидат сделал бы, если бы действовал.
Решение о выкатке принимается по `candidate_only`.

Обе ручки административные, подробности и смысл полей — в
[policies.md](policies.md).

Что меняется в ответе `/v1/scan`: у выключенного правила признак не появляется,
а число отсечённых совпадений видно в `engines.yara.suppressed`. Поле есть
только когда что-то отсечено — иначе разбор старого скана не объяснить:
правило было, признака нет, и непонятно, промолчало оно или его выключили.

## GET /v1/lookup/{sha256}

Вердикт по хэшу без загрузки тела. `404` — файл не сканировался. Дешёвый способ
для бота проверить повторный форвард до скачивания из Telegram.

## Формат ответа

```json
{
  "scan_id": "9f2c...",
  "sha256": "3b1a...",
  "status": "done",
  "verdict": "suspicious",
  "score": 45,
  "findings": [
    {"stage": "structure", "code": "PDF_OPENACTION", "severity": "high", "score": 45,
     "detail": "маркер /OpenAction"}
  ],
  "sanitized": {
    "ref": {"backend": "s3", "bucket": "vulnscan-clean", "key": "9f/9f2c....pdf"},
    "profile": "standard",
    "transforms": ["root/OpenAction", "strip_metadata"],
    "original_sha256": "3b1a...",
    "sanitized_sha256": "77de..."
  },
  "engines": {"clamav": {"status": "OK", "version": "ClamAV 1.4.1/27..."}},
  "stages": [{"stage": "filetype", "elapsed_ms": 4, "ok": true}],
  "elapsed_ms": 312,
  "policy_version": "2026.08.1",
  "from_cache": false
}
```

Расшифровка кодов из `findings` — в [справочнике признаков](findings.md).

### Вердикты

| `manual_review` | проверка не завершилась, случай в dead-letter и ждёт разбора; файл считать непроверенным |

Расшифровка кодов из `findings` — в [справочнике признаков](findings.md).

### Вердикты

| `verdict` | Что делать боту |
|---|---|
| `clean` | отдать пользователю санитизированный файл |
| `suspicious` | отдать санитизированный, оригинал не отдавать |
| `malicious` | не отдавать ничего, `sanitized` отсутствует |
| `unsupported` | формат не обрабатывается; содержимое не проверено |
| `encrypted` | требуется пароль, содержимое не проверено |
| `error` | сбой сервиса; поведение задаёт `on_timeout` |

`verdict` — это детект, а не политика. Решение «блокировать/пропустить» принимает
клиент, опираясь на `score` и свои пороги.

### Поле `shadow`

`"shadow": true` означает, что сервис работает в теневом режиме: вердикт честный,
но **действовать по нему не следует**. Клиент обязан пропустить файл и отдать
обезвреженную копию, даже если вердикт `malicious` — копия для таких файлов в
этом режиме создаётся специально.

Смысл — измерить долю ложных срабатываний на реальном потоке, не задев
пользователей. Отчёт: `GET /v1/ops/shadow`, подробно — в
[policies.md](policies.md).

### Непроверяемые файлы

`unsupported` и `encrypted` означают, что содержимое **не проверялось**. Это не
мягкая версия `clean`:

- `sanitized` у таких ответов всегда `null` — обезвреженного файла не существует;
- `score` поднят минимум до порога `suspicious`, чтобы пороговая политика на
  стороне клиента не приняла непроверенный файл за почти чистый;
- никакой режим отказа не может превратить их в `clean`.

**Правило для клиента: если `mode` не `detect`, а `sanitized` пустой — оригинал
дальше не передавать.** Это относится и к `encrypted`/`unsupported`, и к любому
ответу со `status: failed`.

Отдельно: вердикт `clean` выдаётся только когда проверка действительно
состоялась. Если обязательная стадия упала или не уложилась в таймаут, ответ
будет `suspicious` (или `malicious` при `fail-closed`) с признаком
`STAGE_FAILED` либо `STAGE_TIMEOUT` в `findings`.

PDF с владельческим паролем (пароль пользователя пуст) непроверяемым не считается:
содержимое читается, файл проверяется и санитизируется как обычный, а в `findings`
появляется `PDF_ENCRYPTED_OWNER`.

## Служебные ручки `/v1/ops`: что видно и кому

**Подпись обязательна всегда**, даже при `REQUIRE_SIGNATURE=false`. Но одной
подписи мало: каждая ручка здесь отдаёт данные **тенанта вызывающего**, а
всех тенантов видит только административный ключ.

| Ручка | Обычный ключ | Административный ключ |
|---|---|---|
| `GET /v1/ops/dlq` | свои записи | все |
| `GET /v1/ops/dlq/size` | `404` | глубина очереди |
| `GET /v1/ops/shadow` | свой учёт | сводка по всем |
| `GET /v1/ops/allowlist` | свои и общие записи | все |
| `GET /v1/ops/rules/canary` | `404` | отчёт по набору-кандидату |
| `GET·POST·DELETE /v1/ops/rules/disabled` | `404` | выключить и вернуть правило |
| `POST /v1/ops/allowlist` | только себе | себе, тенанту, всем (`*`) |
| `DELETE /v1/ops/allowlist/{sha256}` | только свою запись | любую |

Так было не всегда: до M7.7 хватало любой подписи. Ломающим изменение не
считаем — сузилась выдача, а не формат ответа, и ни один документированный
вызов от своего имени не перестал работать.

## GET /v1/ops/dlq

Файлы, которые не удалось проверить. Новые первыми, параметр `limit` (1-500).

```json
[{
  "scan_id": "01J...",
  "sha256": "b3f1...",
  "reason": "parser_crash",
  "verdict": "suspicious",
  "detail": "процесс оборвался на стадии structure",
  "stage": "structure",
  "delivered": 1,
  "tenant": "team-a",
  "source": {"backend": "s3", "bucket": "quarantine", "key": "b3/b3f1..."}
}]
```

Веса признаков и пороги настраиваются на стороне сервиса (`WEIGHTS_FILE`,
политика тенанта), поэтому один и тот же файл может дать разный `score` разным
тенантам. Коды признаков при этом стабильны и являются частью контракта.

Причины: `job_abandoned` (исчерпан лимит доставок), `parser_crash` (разбор обрывает
процесс), `scan_failed` (ошибка, вызванная файлом). Содержимого файла в записи нет —
только ссылка на объект в карантине.

`GET /v1/ops/dlq/size` отдаёт глубину очереди — на неё вешается алерт. Ручка
административная: величина общая, а по одному тенанту её пришлось бы считать
перебором всего потока на каждый запрос.

## Список доверенных файлов

Снимает блокировку с конкретного файла без выката релиза — для случаев, когда
разбор показал ложное срабатывание.

```http
POST /v1/ops/allowlist?ttl_days=7
{"sha256": "3541b7...", "reason": "разобрано: договор клиента", "author": "timur"}
```

Автор и причина обязательны, срок ограничен (по умолчанию 30 дней, максимум
365). Поля `created_at` и `expires_at` проставляет сервер — назначать себе срок
жизни тот, кто вносит запись, не может.

`GET /v1/ops/allowlist` — действующие записи, ближайшие к истечению первыми.
`DELETE /v1/ops/allowlist/{sha256}?author=...` — отозвать.

Что происходит с файлом из списка:

- вердикт перестаёт быть `malicious` и становится `suspicious`;
- **признаки остаются видны** — оператор должен понимать, что именно было
  перекрыто вручную;
- в ответе появляется `"allowlisted": true`;
- файл всё равно пересобирается, и пользователь получает обезвреженную копию;
- каждое применение пишется в лог с автором и причиной.

Запись `tenant` ограничивает действие одним клиентом. Кто его назначает:

- **обычный ключ** — только своего тенанта. Не указали поле — подставится он
  же; указали чужого или `*` — `403`. Молча сузить нельзя: попросивший `*`
  решил бы, что разрешил файл всем, и вернулся бы к разбору только когда
  сосед снова упрётся в блокировку;
- **административный ключ** — любого, в том числе `*` (по умолчанию).

Записи разных тенантов по одному файлу независимы: своя перекрывает общую, а
удаление своей не снимает разрешение у соседа.

## GET /v1/ops/shadow

Отчёт теневого режима: сколько файлов проверено и скольким отказали бы, если бы
блокировки были включены. Содержимого файлов нет — только усечённые хэши, по
которым исходник ищется в карантине.

Учёт ведётся по тенанту. Общий счётчик здесь не просто раскрывал бы соседей —
он давал неверный ответ: теневой режим включают по одному тенанту, значит
общая доля «заблокировали бы» описывала поток тех, у кого он включён, а
выдавалась за долю спрашивающего. Администратор получает сводку сложением.

## GET /v1/lookup/{sha256}

Дешёвая проверка по хэшу до загрузки тела файла. Параметры: `profile`, `tenant`.

Отвечает только при полном попадании в оба уровня кэша: без тела файла прогнать
антивирус на свежих базах невозможно. `404` означает «вердикт неизвестен», а не
«файл чист».

## Приём коллбэка

Результат приходит `POST` на `callback_url` с телом `ScanResult` и подписью.
Публичный адрес не обязателен: если клиент развёрнут рядом, достаточно
внутреннего.

Что должен делать приёмник:

- **проверять подпись до разбора тела** — иначе он принимает что угодно;
- **отвечать `2xx` при верной подписи**, даже если результат уже обработан:
  иначе сканер будет ретраить то, что вы уже приняли;
- **дедуплицировать по `scan_id`** — коллбэк доставляется не менее одного раза,
  и повтор не должен приводить ко второму действию;
- **не полагаться на коллбэк как на единственный путь** — `GET /v1/scan/{id}`
  остаётся подстраховкой на случай, если он не дошёл.

Последние два пункта связаны: если опрос идёт параллельно с ожиданием
коллбэка, право ответить надо разыгрывать атомарно, иначе оба сработают.

## Подпись

Входящие запросы (`/v1/scan/ref`) и исходящие коллбэки подписываются HMAC-SHA256:

```
X-Vulnscan-Timestamp: 1756200000
X-Vulnscan-Signature: sha256=<hex>
```

Подписывается строка `{timestamp}.{body}`. Окно валидности — 300 секунд.
Проверяйте подпись коллбэка на своей стороне до разбора тела.

## Обработка на стороне клиента

- Дедуплицируйте по `scan_id`: при синхронном `200` коллбэк всё равно придёт.
- Повторная отправка того же файла возвращает тот же `scan_id` и не запускает
  вторую проверку — ни пока идёт первая, ни после неё.
- Ставьте таймаут чуть больше `wait_ms` и circuit breaker — при недоступности
  сканера у бота должно быть заранее решённое поведение, а не зависший апдейт.
- `Idempotency-Key`: необязательный заголовок. Если в нём передан sha256 файла,
  сервис сверит его с содержимым и ответит `400` при расхождении — так ловится
  обрезанная загрузка. Ключи произвольного вида принимаются и игнорируются:
  дедупликация всё равно идёт по содержимому.


## Административные ручки

Требуют ключа с признаком `admin`. Обычный ключ тенанта сюда не проходит и
получает `404`: иначе клиент выписывал бы себе ключи и менял себе политику —
тот же `fail-open` полем в запросе, только окольным путём.

Наружу эти ручки не публикуются: заведение тенантов делается из внутренней сети.

| Ручка | Что делает |
|---|---|
| `POST /v1/admin/keys` | выпускает ключ; секрет генерируется сервером |
| `DELETE /v1/admin/keys/{key_id}` | отзывает ключ, действует сразу |
| `GET /v1/admin/keys` | состав реестра **без секретов** |
| `PUT /v1/admin/tenants/{tenant}/policy` | меняет пороги и лимиты тенанта |
| `GET /v1/admin/tenants` | тенанты и их переопределения |

Секрет показывается **один раз**, при выпуске. Повторно сервис его не отдаёт, и
ручки «покажи ключи целиком» нет: она превратила бы одну утечку во все сразу.

Отзыв и правка политики подхватываются без перезапуска — скомпрометированный
ключ нельзя оставлять действующим до окна обслуживания.

Собственный ключ отозвать нельзя: администратор одним запросом отрезал бы себе
доступ.
