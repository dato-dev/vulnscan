# Библиотека `vulnscan_client`

Справочник по Python-клиенту: что он берёт на себя, как читать вердикт и что
происходит, когда сервис недоступен.

Библиотека не обязательна — протокол открыт и описан в
[protocol.md](protocol.md). Она снимает три места, где интеграция ошибается
молча: сборку подписи, повторы и разбор вердикта.

Зависимость у неё одна — `httpx`. Ни OpenTelemetry, ни наш общий код она не
тянет: то, что едет к чужой команде, не должно тащить за собой наш стек.

## Быстрый старт

```python
from vulnscan_client import VulnscanClient

async with VulnscanClient(base_url=..., key_id=..., secret=...) as client:
    outcome = await client.scan(content, filename="скан.pdf")

    if outcome.blocked:
        return "Вложение заблокировано"
    if not outcome.safe:
        return "Вложение не удалось проверить"
    clean = await client.download_clean(outcome.scan_id)
```

Три ветки, а не две, — это и есть главное отличие правильной интеграции от
неправильной. Подробно — в разделе [Разбор вердикта](#разбор-вердикта).

## Создание клиента

```python
VulnscanClient(
    base_url,           # адрес сервиса, без завершающей косой черты
    key_id,             # идентификатор ключа
    secret,             # секрет; из окружения или хранилища, не из кода
    *,
    timeout_s=30.0,     # таймаут одного HTTP-запроса
    wait_ms=2000,       # сколько сервис ждёт вердикт, прежде чем ответить 202
    callback_url=None,  # куда прислать результат вебхуком
    retries=3,          # попыток на запрос
    trace_context=None, # функция, возвращающая текущий traceparent
    verify=True,        # путь к сертификату своего CA, если TLS выпущен не публичным
)
```

Клиент держит пул соединений, поэтому его создают **один раз на процесс**, а не
на запрос. Закрывать — через `async with` либо `await client.close()`.

Про два параметра стоит сказать отдельно.

**`wait_ms`** — не таймаут, а верхняя граница синхронного ответа. Не уложились —
придёт `202` и `pending=True`, что нормально. Сервис ограничивает это значение
сверху политикой тенанта: попросить больше разрешённого можно, получить — нет.

**`trace_context`** — необязательная функция без аргументов, возвращающая
`traceparent` в формате W3C. Если её передать, наш сервис продолжит ваш трейс
вместо того, чтобы начинать свой, и запрос будет виден одним деревом от вашего
кода до стадий проверки. С OpenTelemetry это выглядит так:

```python
from opentelemetry import trace

def traceparent() -> str | None:
    span = trace.get_current_span()
    ctx = span.get_span_context()
    if not ctx.is_valid:
        return None
    return f"00-{ctx.trace_id:032x}-{ctx.span_id:016x}-{ctx.trace_flags:02x}"

client = VulnscanClient(..., trace_context=traceparent)
```

Импорта OpenTelemetry внутри библиотеки нет намеренно: трассировку ведёт тот,
кто её ведёт, и навязывать её остальным незачем.

**`verify`** — если сервис стоит за TLS, выпущенным своим центром
сертификации (внутренняя сеть, Gateway API в кластере), передайте путь к
сертификату этого центра. Путь стоит пропустить через `resolve_ca_file`:

```python
from vulnscan_client import resolve_ca_file

client = VulnscanClient(..., verify=resolve_ca_file(os.environ.get("CA_FILE", "")))
```

Пустой путь и `/dev/null` (необязательное монтирование в compose) дают
системные центры. Файл, который нельзя прочитать, — `ValueError` с причиной:
нет файла, каталог вместо файла (Docker создаёт его сам, если монтируемого
файла на хосте нет), нет прав у пользователя процесса, путь внутри `/root` у
процесса, запущенного не от root. Без этого та же ошибка приходит как
`PermissionError` из глубины `ssl`, без имени файла и без причины. `verify=False` допустим только на стенде: подпись
запроса проверяет, кто его прислал, но не защищает от посредника, который
прочитает загружаемый документ.

## Методы

### `scan(content, filename, content_type=..., profile=None) -> ScanOutcome`

Отправляет файл. Возвращает готовый вердикт либо `pending=True`, если сервис не
уложился в `wait_ms`.

`filename` обязателен и используется только для определения типа: в ответ он не
возвращается и в наших логах не сохраняется — имена файлов слишком часто
содержат персональные данные.

Заголовок идемпотентности библиотека проставляет сама, из sha256 содержимого.
Повторная отправка того же файла не создаёт новую проверку.

### `result(scan_id) -> ScanOutcome | None`

Забирает результат по идентификатору. `None` означает «нет такого скана» — либо
он не существует, либо принадлежит другому тенанту; различить это нельзя, и это
сделано намеренно.

`None` — **не** «ещё не готов». Незавершённый скан возвращается объектом с
`pending=True`.

### `download_clean(scan_id) -> bytes`

Скачивает обезвреженную копию. Бросает `VulnscanError`, если копии нет: файл
проверяли в режиме `detect` либо он оказался непроверяемым, и пересобирать было
нечего.

### `download_clean_copy(scan_id) -> CleanCopy`

То же, но вместе с типом и именем, которые назвал сервис: `content`,
`content_type`, `filename`. Нужен, когда копию отдают дальше — посетителю,
в хранилище. Формат копии не обязан совпадать с присланным: GIF
пересобирается в PNG, а заблокированный файл при `deliver_blocked: "strict"` —
в `strict`. Расширение, взятое у исходника, дало бы файл, который не
откроется.

`filename` состоит из идентификатора проверки и расширения; имени исходного
файла в нём нет. Путь и кавычки из заголовка отброшены, но класть имя на диск
без своей проверки всё равно не стоит.

### `verify_callback(secret, body, headers) -> dict`

Функция, а не метод: она нужна на стороне обработчика вебхука, где клиента может
не быть вовсе.

```python
from vulnscan_client import verify_callback, CallbackVerificationError

async def webhook(request):
    body = await request.body()          # сырые байты, до разбора JSON
    try:
        payload = verify_callback(SECRET, body, dict(request.headers))
    except CallbackVerificationError:
        return Response(status_code=401)
    ...
```

**Именно сырые байты.** Разбор и повторная сериализация меняют их — порядок
ключей, пробелы, экранирование — и подпись не сойдётся. Во многих фреймворках
тело к этому моменту уже разобрано, и его приходится запрашивать отдельно.

Проверка обязательна: эндпоинт без неё принимает вердикт от кого угодно.

## Разбор вердикта

`ScanOutcome` — то, ради чего библиотека существует. Три свойства, и между ними
легко ошибиться.

| Свойство | Истинно, когда |
|---|---|
| `blocked` | `verdict == "malicious"` — файл отдавать нельзя |
| `safe` | `verdict == "clean"` — проверен, признаков нет |
| `unscannable` | `unsupported` или `encrypted` — **проверить не удалось** |

> **`not blocked` и `safe` — разные вещи.**

Между ними помещаются четыре состояния: `suspicious` (признаки есть, порог не
пройден), `unsupported`, `encrypted`, `error`. Ни одно не заблокировано, и ни
одно не безопасно.

Это самая частая ошибка интеграции и единственная, которая не проявляется
никак: код работает, тесты проходят, файлы принимаются. Разница видна только
тогда, когда через форму проходит то, что не должно было пройти.

Поэтому `safe` — не отрицание `blocked`, а отдельное свойство с положительным
списком. Незнакомый вердикт, добавленный в сервисе позже, у старого клиента
окажется небезопасным: ошибка приведёт к лишней строгости, а не к пропуску.

Остальные поля: `scan_id`, `verdict`, `score`, `status`, `pending`, `sanitized`,
`findings` (список признаков с кодами) и `raw` — ответ целиком, если нужно
что-то, чего библиотека не разобрала.

`score` отдаётся отдельно от вердикта сознательно: сервис детектит, политику
применяет клиент. Хотите блокировать строже нашего порога — смотрите на балл.

## Отложенный результат

`pending=True` — штатный исход, а не ошибка. Файл принят, вердикта пока нет.

Забрать его можно двумя способами.

**Опросом.** Простой путь, годится там, где ответ нужен в том же запросе — форма
на сайте, например.

```python
outcome = await client.scan(content, filename=name)
for _ in range(6):
    if not outcome.pending:
        break
    await asyncio.sleep(1.0)
    outcome = await client.result(outcome.scan_id) or outcome
```

**Коллбэком.** Правильный путь для фоновой обработки: задайте `callback_url` при
создании клиента. Адрес должен быть в списке разрешённых для вашего ключа, иначе
файл не примут — проверка идёт на приёме, а не при доставке.

Так и не дождались — это **не** повод считать файл чистым. Непроверенное
вложение либо не принимается, либо помечается непроверенным, но не проходит как
безопасное.

## Когда сервис недоступен

Библиотека повторяет только то, что осмысленно повторять: `429` и `5xx`, а также
сетевые сбои. Задержка удваивается от 0.5 секунды. `400` и `401` не повторяются
— через секунду будет то же самое, а квоту повторы расходуют.

Исчерпав попытки, метод бросает `VulnscanError`. Иерархия исключений короткая:

```
VulnscanError                  сервис недоступен или ответил ошибкой
└── CallbackVerificationError  коллбэк не прошёл проверку подписи
```

Ловить `VulnscanError` обязательно. Решение, что делать дальше, — ваше, но
вариантов ровно два: **не принимать вложение** либо **принять и пометить
непроверенным**. Принять как чистое нельзя.

Так это выглядит в примере с формой обратной связи
([examples/feedback-site](../examples/feedback-site)):

```python
try:
    outcome = await client.scan(content, filename=name)
except VulnscanError:
    return "Не смогли проверить вложение. Попробуйте чуть позже."
```

Тот же принцип, что и внутри сервиса: ни один путь исполнения, кроме успешно
завершённой проверки, не имеет права дать «чисто».

### Диагностика `401`

Ответ на неверную подпись одинаков во всех случаях — иначе он подсказывал бы
подбирающему, насколько тот близок. Порядок проверки такой:

1. **часы.** Расхождение больше 300 секунд отклоняется; это самая частая
   причина;
2. идентификатор ключа и секрет — из того же выпуска, а не от разных;
3. если подпись собирается своим кодом, а не библиотекой, — сверьтесь с
   векторами: [tests/vectors/protocol.json](../tests/vectors/protocol.json).
   Там байты канонического запроса и ожидаемые подписи, и расхождение видно
   сразу, без обращения к нам.
